# ADR-0005 — 扁平标量 schema，规避容器创建冲突

日期：2026-09-19 · 状态：已采纳（M4 实测后修订 ADR-0004 的实现方式）

## 背景

块级 CRDT 首版实现用嵌套容器承载文档：
`root/order = List<bid>`、`root/blocks = Map<bid, Text>`。
测试暴露严重缺陷：**两端离线各自打开同一篇文档时，会各自创建同名的 `order`/`blocks` 容器对象；合并时容器对象本身冲突，一方容器胜出，另一方的块全部不可见**（表现为 B 的编辑凭空消失、块丢失）。

这不是顺序算法的 bug，而是"独立创建同名容器"这一模式的固有问题。

## 决策

文档存储改为**扁平标量 schema，不使用任何嵌套容器对象**：

| 键 | 类型 | 含义 |
|---|---|---|
| `t` | Str | 标题 |
| `d:<bid>` | Str(JSON) | 块内容，块级合并单元 |
| `o:<bid>` | Str | 块顺序键（分数索引，字典序即顺序） |

- 顺序在物化时按 `(order_key, bid)` 排序**派生**，而非存储为 List。
- 分数索引 `fraction_between(prev, next)` 生成严格居中的字典序键；并发同位插入产生相同键，由 `bid` 做确定性 tiebreak，双方块都保留。
- 无容器 → 无"容器创建冲突"；键级并发是标量 LWW，语义清晰。

## 验证

- 并发编辑同一文档的**不同块**：双方修改都保留。
- 并发**新增**不同块：双方新增都保留。
- 两库经同步协议收敛；跨文档并发完整合流。
- 分数索引单调性与相等边界（不死循环）单测通过。

## 后果

- 块级合并成为协作主路径（ADR-0004 的 V1 限制解除）。
- 文档顺序由派生计算得到，读取成本 O(块数 log 块数)，对知识文档量级无感。
- 同一块被两端并发编辑仍会产生两个块（各自新 bid），无数据丢失但需人工合并——记录为已知边界，后续可加"同源块归并"启发式。
